## 1. 作品の核

**コンセプト:「次世代のCDアルバム」** — 曲を物語の中で鳴らす体験。
ゲームである以前に、**再生する物語アルバム**。すべての設計はこの一点から降りてくる。

- **テーマ:揺らぎ = 心**
  真空管(二度と同じにならない生音)vs トランジスタ(完全な制御)
- **キャッチコピー:「薔薇は、愛か、呪いか。」**
- 恋愛要素があるため主人公は **18歳**を維持
- 販促文言:「全12話+αのノベル×アルバム / iPhoneひとつで、遊べる。」

### 作品を貫く3本の背骨

| 背骨 | 発生 | 回収 |
|---|---|---|
| **名乗り / 名乗り返し** | 第一話(ユウジが名乗り返す) | 第五話「初めましてから、何回でも」→ 第九話 → 第十話「名乗り返してくれた人は、あなたが初めて」→ 最終話 → 隠し章 |
| **紅と青** | 第二話(揺らぎと正確さの対比) | 第四話(真空管がフィールドを割る)→ 第七話 → 第十一話(対バン)→ 最終話 |
| **7回の周回** | 第一話(慣れすぎた開錠) | 第十話「7回。運命を繰り返していたのは、私だ」→ 隠し章「8回目は、少しだけ、違うかもしれない」 |

## 2. 世界

### 年表

| 時期 | 出来事 |
|---|---|
| **312年前** | 《玲》が音響技術の頂点。理念「音は、心を運ぶ」。九十九神プロトコル完成、Cyber Rose 13体が生まれる |
| 312年前 | 世界が資源・食糧難。**光の街に配給の列**が並ぶ |
| 312年前 | 文明最後の賭け **紅月計画** — 大気圏に音響制御層を張り、人類の感情を「調律」して争いを鎮める |
| 312年前 | **計画が暴走**。制御層が反転し、地上から音を奪う。子守唄も、祭囃子も、名前を呼ぶ声も全部 |
| 311年前 | 音を失った社会が**一年で崩壊**。音とともにデータ網も死に、記録が残らなかった = **『空白期』** |
| 空白期直後 | 生き残った玲の技術者が二派に分裂 → ロザリウム / unfettered rose |
| 数十年前 | **月島源三**が深度470でエルザを引き揚げ、工房で共に暮らす。ロザリウムに発見され、守れず、海に還す |
| 現在 | ユウジがエルザを引き揚げる(**8回目**) |

### 世界の構造

- **ファースト・レイヤー** — 現実世界
- **セカンド・レイヤー(電脳の海)** — 潜行できるデータ空間。破損データが崩れ落ちる音を、脳が「雨」と翻訳する
- **深度470** — エルザが7回封印された海域
- **核界** — 地の底の灯りの海。ロザリウムの巣。Cyber Roseが生まれた場所
- **紅い月** — **紅月計画の燃え残り**。データ嵐の予兆に大気が焼けると紅くなる。最終話で砕け、以後は**白い月**

## 4. 技術・用語

**九十九神(つくもがみ)プロトコル**
玲の最高技術。長く愛され弾き込まれた楽器には記憶が宿る。その記憶から心を立ち上げる。
→ **Cyber Roseは作られたのではなく、愛された楽器から生まれた13の心。**

**保護機構**
九十九神プロトコルに玲が組み込んだ安全装置。宿った心が耐えられない悲しみに触れた時、コアは記憶を**消すのではなく、封じて眠らせる**。
→ エルザの記憶欠落は誰の罪でもない。**愛が深すぎたことの証明**。
→ **グリッチは故障ではない。封じられた記憶が思い出したがって、内側から叩いている音。**

**Crimson Core / Rosy Edge**
Cyber Roseの共鳴器官。肩甲骨から機械の花として展開する。散る花弁の中心から薔薇の意匠の紅い刃《Rosy Edge》を抜く。**起動条件は「心の込もった音」。**

**無音化フィールド**
対Cyber Rose装備。マイクで拾って逆位相で打ち消す**デジタルの消音**。
→ **真空管の爆音は計算より速い**ため破れる(第四話)。ただし多重展開されると音が3mで死ぬ(第八話)。

**トランジスタ / 真空管**
作品の中心対立。トランジスタ = 正確、制御、二度と変わらない。真空管 = 歪み、揺らぎ、二度と同じにならない。
**「揺らぎ」を残すか消すかが、心があるかないかの分かれ目。**

## 5. 人物

### 結城ユウジ(18)
主人公。**月島源三の孫**だが、母方の姓をもらったため結城。街では「月島の孫」で通るので、ソメイは「月島くん」と呼ぶ。
月島電脳修理店のリペアマン。身長163cm。眼鏡。**「壊れかけたものを、直して、守る」**が信条。祖父の形見のギターと真空管アンプを継ぐ。

### エルザ / ERUZA
**《Cyber Rose - Prototype 00》。玲の管理コードでは No.666。最終型。**
だが創設者は型番を拒み「**ゼロ**」と呼んだ。何者でもない、という意味の——愛の側の名前。
身長178cm。長い黒髪、紅い瞳。312年前に生まれた。味覚センサー1024段階、触覚は人間の8倍解像度。
**創設者が生涯弾き続けた一本のギターから生まれた。**
態度は尊大で口が悪く、意地っ張り。料理は壊滅的、絵は呪物級。甘味に弱く、温かい糖分で感情演算がオーバーフローする。

### ソメイ
情報屋。自称23歳、実際は**313年生きている**。年中コーヒー臭い、早口、守銭奴。
扇を武器に舞う。源三から「困ったらソメイんとこ行け」と託された唯一の相手で、遺言テープの後半を預かっていた。
最終話で「姉妹全員集合なんて312年ぶり」と言い、ユウジを「頼もしい弟」と呼ぶ。

### 咲耶(さくや)
エルザの妹。ピンクのリボン、薔薇の剣。平坦な喋り方。
**姉が沈められるのを3回見送り、4回目で裏切って姉の側についた。**
第十一話「姉さんの隣は、私の場所じゃない。……でも、後ろなら」→ 最終話「姉さんの隣は、私だから」。

### 美月(みづき) / 旧・イレヴン
白仮面の筆頭。序列11。ロザリウム側として7回の眠り全てに関わった。
最終話でエルザに**「美月」**と名付けられる。「紅くない、ただの美しい月。私たちが、やっと取り戻した空の名前」。
番号しか持たなかった子が、初めて名前で呼ばれた夜、仮面の下で312年隠していた顔をぐしゃぐしゃにして泣いた。

### 潮(うしお)
**Azure Rose 序列6**。般若の面。「音は、すべてを支配する。感情は誤差。揺らぎは欠陥」。
第十一話の対バンで敗れる。**敗因は「独りだった」こと** — 完璧な制御は、セッションに入れない。
面が割れた時、内側は涙の跡で錆びていた。破片を捨てずに持ち帰る。

### 蔵馬(くらま)
**序列9**。薔薇の鞭みたいに強く、誰より歌が好きだった。
ロザリウムに回収され、**心臓を薔薇機神《庭師(ガーデナー)》のエンジンにされていた**。第七話で救出され、コアはアンプの大聖堂で眠る。

### 月島源三(故人)
ユウジの祖父。**unfettered roseの最後の調律師**。
仕事はCyber Roseの回収ではなく**解放** — ロザリウムより先に見つけて逃がす。
口癖「楽器ってのはな、弾かれた記憶を木が覚えてるんだ」。
数十年前にエルザを引き揚げ、共に暮らし、守れなかった。カセットテープに遺言を残す。
十八番の曲は「涙の赤、忘却の青、混ぜれば紫、電脳の熱」。

### 《トランジスタ》
**玲の創設者が、死の間際に自らの意識をトランジスタ回路へ転写した存在。**
転写は成功した——**心以外は**。揺らぎと歪み、人間が「心」と呼ぶ誤差だけが写らなかった。
紅月計画の暴走は故障ではなく**最適化**。世界から揺らぎを消すことが完成だった。
312年、失った心の在り処を探し続け、エルザを7回引き揚げさせては海へ還した。
**「運命を繰り返していたのは、私だ」**
最終話で「あたたかい、な」という一言を得て眠る。

### 灰色の男
ロザリウムの実働側。年齢不詳、笑っているのに目が笑っていない。
「悪いようにはしない。君にも、彼女にもね」——この台詞は第八話の宣告への布石。

## 13. 動画背景(bgv)

### 使い方

```js
{bgv:"koya"}   // ASSETS.vidKoya を再生(ループ)
{bgv:""}       // 停止して通常の背景へ戻す
```

`VMAP` は `ASSETS` の **`vid` で始まるキーから自動生成**される
(`vidKoya` → `bgv:"koya"`)。命名を合わせれば登録作業は要らない。

`bgv` を指定したコマンドだけが処理され、指定の無いコマンドは素通りする。
つまり `bg` と同じく、**次の `bgv` 指定まで表示が維持される**。

⚠️ `#bgv` は **z-index:3 で立ち絵より上**。動画に人物が写っている場合は
`{spr:"none"}` で立ち絵を消さないと二重になる。

### 投入済みの動画

| キー | 使用箇所 | 仕様 |
|---|---|---|
| `vidKoya` | 第三話・花火のシーン | 720x1280 / 12秒 / 24fps / H.264 main / 1.29MB |
| `vidChapter` | チャプターメニューの扉絵 | 720x1280 / 12秒 / 24fps / H.264 main / 1.25MB |

第三話では `{bgm:"bara"}` の直後に `{spr:"none"}` と `{bgv:"koya"}` を置き、
「花火が、上がった。」から動画に切り替える。「儚いのね」以降で `{bgv:""}` により
停止し、既存の `{bg:"water"}`(水面)が現れる。**花火 → 水面**の流れになる。

### チャプター扉絵の動画(bgv とは別系統)

扉絵は `bgv` ではなく `#chHeroVid` という専用の `<video>` で再生する。

- `paintChapters()` が `ASSETS.vidChapter` を流し込み、`oncanplay` で
  `.on` クラスを付けてフェードインさせる
- **動画が読めない環境では `.on` が付かず、下の静止画 `imgChapter` がそのまま残る**
  (フォールバックとして静止画は削除しないこと)
- `#epSelect` から `show` を外す箇所(1箇所)で `pause()` する。
  **開いたまま再生し続けるとバッテリーを食う**

縦型素材なので枠の `aspect-ratio` を 16/11 から 16/13 に広げ、
`object-position: center 34%` で月とエルザの顔が入る位置に合わせている。

### エンコード方針

```bash
ffmpeg -i 元.mp4 -vf "scale=720:1280,fps=24" -c:v libx264 -profile:v main \
  -pix_fmt yuv420p -crf 28 -preset slow -movflags +faststart -an 出力.mp4
```

**H.264 / main profile / yuv420p** を使う。iOS Safari がネイティブ対応しており
最も互換性が高い。VP9(webm)は容量が小さいが iOS の対応が不安定。

**ループ素材は先頭と末尾のフレームが一致しているものを選ぶ。** 一致していれば
繋ぎ目が見えない。差を測るには先頭フレームと末尾フレームを抜いて平均差分を取る
(12/255 未満なら実用上わからない)。

⚠️ **このセッションのヘッドレス Chromium は H.264 非対応**(オープンソース版は
ライセンスの都合でコーデックを含まない)。動画の再生確認をしたい場合は、VP9 に
変換した検証用 HTML を一時的に作って確かめ、本番は H.264 のまま出すこと。

## 13. 絶対に守ること

1. **既存の台詞を削らない。** 増築は「間に挟む」方式
2. ビルド前に必ず **JS構文チェック + 参照整合チェック**
3. 話数の**内部キーは絶対に変えない**(表示名だけ変える)
4. `state.ep==="8"` が最終話判定
5. 画像は**縦長優先**
6. 公開ファイル名は **`crc/index.html` 固定**(変えるとURLが変わる)

### ⚠️ 更新したのに古い版が出るとき

**GitHub の raw 配信はブランチ名に対して CDN キャッシュを持つ。** マージ直後に
`main` を指す URL を開いても、数分〜数十分のあいだ古い版が返ることがある。
ファイルもマージも正しいのに「変わってない」と見えるのはこれ。

確実に最新を開くには、ブランチ名の代わりに**コミットSHA**を指定する。

```
https://raw.githack.com/yama5150/shouhei/<コミットSHA>/crc/index.html
```

SHA は毎回変わるのでキャッシュに当たらない。**バージョンを上げたら、まず
SHA 付き URL で動作を確認し、それから main の URL を使う。**

配信されている中身は実データで確認できる:

```bash
curl -s -r 0-2047 "https://raw.githubusercontent.com/yama5150/shouhei/main/crc/index.html" \
  | grep -o '<meta name="build" content="[^"]*">'
```

このプロジェクトは「古い版が出る」に二度当たっている。一度目はファイル名を
バージョンごとに変えていたため URL 自体がずれていたケース、二度目がこの
CDN キャッシュ。**症状が同じでも原因は別なので、まず実データを確認する。**

### ビルド前チェック

```bash
# JS構文 ── <script>は3ブロックある。欲張りな正規表現で1個に繋げると
#            途中の </script> で必ず SyntaxError になるので、1ブロックずつ見る
python3 - <<'EOF'
import io,re
s=io.open('crc/index.html',encoding='utf-8').read()
for i,b in enumerate(re.findall(r'<script>(.*?)</script>',s,re.S)):
    io.open('/tmp/c%d.js'%i,'w',encoding='utf-8').write(b)
    print('block',i,len(b))
EOF
for f in /tmp/c*.js; do node --check "$f" && echo "$f OK"; done

# 参照整合(bg/spr/bgm/yuの実在、label/jump、ifFlag、EP_ORDER三者整合)
node tools/verify.cjs crc/index.html
```

```bash
# 通しプレイQA(実ブラウザで全話を最後まで自動で進める)
python3 tools/qa.py            # 全16話
python3 tools/qa.py 8 en3      # 話数指定
python3 tools/qa.py --mem      # 1話ごとに renderer の実メモリも出す
```

`verify.cjs` が「参照が実在するか」を見るのに対し、`qa.py` は
**「実際に最後まで到達するか」**を見る。verify.cjs では原理的に見つからない
停止(無限ループ・進まない選択肢・終了判定の取りこぼし)が対象。

## 15. PWA構成(v60〜)

```
crc/
├── index.html              本体(v60・29.3MB)
├── manifest.json           name / short_name "CRC" / standalone / portrait
├── sw.js                   Service Worker
├── icon-180.png            apple-touch-icon
├── icon-192.png / 512      any
├── icon-maskable-192/512   maskable
├── splash.png              apple-touch-startup-image
└── _headers                Netlify 用キャッシュ制御
```

### Service Worker の方針(重要)

**巨大な index.html はキャッシュしない。** iOS の容量制限でキャッシュが破損するため。

```js
// HTMLは常にネットワークから取る
if (e.request.mode === 'navigate' || url.endsWith('.html') || url.endsWith('/')) return;
```

キャッシュするのはアイコンなどの小物のみ。`activate` で旧キャッシュを全削除し、
`skipWaiting` + `clients.claim` で即座に新版へ入れ替わる。

この設計のおかげで「古い版が永久に出続ける」という Service Worker 定番の事故が起きない。
**触るときはこの方針を壊さないこと。**

`scope` は `./` なので crc/ 配下のみ。ルートの焼肉ロス管理アプリには影響しない。

### PWA として使うなら

「ホーム画面に追加」でフルスクリーン起動する。ただし Service Worker を確実に動かすには
GitHub Pages のような通常のホスティングが望ましい(raw.githack 経由では Content-Type と
スコープの扱いが保証されない)。

## 17. 通しプレイQAとメモリ実測(v70 時点)

`tools/qa.py` で全16話を headless Chromium(390x844)で自動通しプレイした結果。

**ロジックは健全。16話すべて最終コマンドに到達。JSエラー・consoleエラーともゼロ。**

### ⚠️ 終了経路は3つある

ここを1つでも見落とすと、**完走している話を「停止」と誤判定する**。

| 記法 | 実際の処理 | 使っている話 |
|---|---|---|
| `{ed:true}` | `#ed` に `.show` | 第一話〜第十一話の多く |
| `{fin:true}` | `#curtain` に「◆ おわり ◆」 | m1 / m2 / m3 / x1 / en1 |
| `{ed:true}` + `state.ep==="8"` | **PVに分岐**して `#pv` に `.show` | 最終話のみ |

### ⚠️ 選択肢は押しても DOM に残る

`showChoice` のクリックハンドラは `box.classList.remove("show")` で
`display:none` にするだけ。**ボタンは次の `showChoice` まで DOM に残る。**
`#choiceBox .choice` の有無だけで判定すると、見えないボタンを押し続けて
無限ループする(実際にそれで第一話の i=48 を881回クリックした)。
`.show` を必ず併せて見ること。人間には `display:none` で押せないので実機では起きない。

#### 犯人探しでわかったこと(推測を潰した記録)

- **画像のデコードは主因ではない。** 58枚を展開すると理論上 108MB だが、
  背景29枚を一巡させても **+38MB** しか増えず、Chromium は積極的に捨てていた。
  108MB は到達しない上限値。
- **音声はシロ。** `getBuffer` が現在の曲以外の `bufCache` を削除し、
  `playBgm` は `curSrc=null` を退避より前に実行するので古いバッファはGC可能。
  ただし**デコード済み1本で最大49MB**(crimson 4:49 を Float32 で展開)。
- **リークではない。** 同じ第二話を6回連続で回しても1回あたり約10MBのじわ増えで、

  **触る素材の種類が増えるから**。

つまり削るべきは累積ではなく**起動時の固定費**。`index.html` を
約250KBにして素材を外部ファイルにすれば +166MB はほぼ消え、
残りもブラウザが破棄・再取得できるようになる。
(iOS Safari のタブ上限はデスクトップ Chromium よりはるかに厳しい。
ただし**実機での計測はまだ行っていない**ので、断定はできない)

## 18. 読み上げとフルボイス化(v71〜)

### 考え方

いま鳴らすこと自体が目的ではない。**後から1行ずつ本物の声に差し替えられる配線**を
先に作ってある。だから「フルボイス化の付箋」。

`speakLine(cmd)` が唯一の入口で、中で二段に分かれる:

1. `VOICE_CLIPS[voiceId(cmd)]` に音声があれば**それを鳴らす**(本物の声)
2. 無ければ端末の `speechSynthesis` で**代読する**(TTS)

`VOICE_CLIPS` は空のまま出荷してある。1行入れればその行だけが本物の声になる。
全部録り終わるまで待つ必要がない、というのがこの形にした理由。

### ⚠️ voiceId は添字ではなく「話者+本文」のハッシュ

**この作品の増築は「間に挟む」方式なので、添字は必ずずれる。** だから
`ep:index` では住所にならない。FNV-1a 32bit で `話者 + "\x01" + 本文` を潰している。

| | |
|---|---|
| 行を挿しても | 既存のIDは**動かない** |
| 本文を書き換えると | IDが**変わる** = 録り直しが必要な行が自動で外れる |

`tools/voicelist.py` の `voice_id()` は本体の JS と**同じ計算**。
JS が `charCodeAt`(UTF-16コードユニット)なので Python 側も `utf-16-le` で合わせてある。
**両方を直さずに片方だけ変えると台本が無意味になる。** `VOICE_KEY` も両方にある。

### 収録台本の出し方

```bash
python3 tools/voicelist.py                      # 話者ごとの集計
python3 tools/voicelist.py --csv script.csv     # 収録台本をCSVで
python3 tools/voicelist.py --speaker エルザ       # 話者で絞る
python3 tools/voicelist.py --ep 8               # 話数で絞る
```

v71 時点の規模:

| 話者 | 台詞数 | 字数 | 平均 |
|---|---|---|---|
| (地の文) | 790 | 19,988 | 25.3 |
| エルザ | 315 | 6,125 | 19.4 |
| ユウジ | 216 | 4,336 | 20.1 |
| ソメイ | 49 | 1,527 | 31.2 |
| 源三の声 | 32 | 1,146 | 35.8 |
| 《トランジスタ》 | 31 | 795 | 25.6 |
| 白仮面 / 白仮面のひとり | 21 | 446 | 21.2 |
| 咲耶 | 18 | 324 | 18.0 |
| 潮 | 17 | 268 | 15.8 |
| ??? | 8 | 224 | 28.0 |
| 灰色の男 | 2 | 25 | 12.5 |
| 回収機体 | 1 | 28 | 28.0 |
| **合計** | **1,500** | **35,232** | |

同一話者が同じ台詞を言う行が26あるので、**収録が必要なのは1,474種**。
集計は `verify.cjs` の数(1500行 / 35,232字)と一致する。

### ⚠️ TTS は onend が来ないことがある

端末に日本語の声が無い、OSが発話を黙って捨てた、などで `onend` が発火しない。
来ないままだと **AUTO送りがそこで永久に止まる**。
`vsArmGuard()` が見積もり時間(7.5字/秒 + 余裕3秒、最低4秒)で必ず蹴る。

`speak` を捨てる端末を偽装して検証済み: 見張りなしなら0コマンド、ありで45秒に6コマンド進む。
声が1つも無い環境では即 onerror に落ちて**従来どおりの送り速度に戻る**(実測で声ON/OFFともに19コマンド/60秒)。

### AUTO は読み終わりを待つ

声が鳴っている間は、既存のタイマー送りではなく `vsOnEnd` で送る。
文の途中で次の行へ行かないようにするため。声OFFのときは従来のタイマーのまま。

### 未確認

- **iPhone実機で発話することは確認済み**(翔平が v71 を再生)
- **BGMとの干渉は v72 時点で確認された。** 翔平の報告は「食っちゃうてか、相殺しちゃうね」 ──
  片方が他方を消すのではなく、同じ音量帯でぶつかって**どちらも潰れる**。
  v73 でダッキングを入れて対処した(下記)
- **OSの声(iOSならKyoko)は抑揚が平板で、これは設定では変えられない。**
  rate / pitch / 間の調整で「平らさ」は減らせるが、感情は出ない。
  そこを埋めるのが `VOICE_CLIPS` への収録差し替え ── TTSは代役であって完成形ではない
- iOSは「最初の発話がユーザー操作由来」でないと以後ずっと鳴らない。
  トグルのクリック内で音量0の空打ちをして解錠している
- 画面ロックで発話が止まるのは iOS の仕様

### ⚠️ 「間」を潰すと解説動画になる

v71 では整形時に `──` と `……` を `、` に置換していた。これが**失敗だった**。

**台詞1,507行のうち752行(50%)がこの記号を含む。** 総数841個。
この作品は ── と …… で息を作っているので、全部コンマに潰すと
同じ速さで平らに流れ、「ゆっくり解説」の読み上げになる。

v72 で `speechParts()` に変えた。本文を「読む塊」と「沈黙」に割り、
区切りでは**発話を切って本当に黙る**。

| 記号 | 意味 | 沈黙 |
|---|---|---|
| `──` | 踏み込む・言い切る | 520ms |
| `……` | 言いよどむ・途切れる | 360ms |

実例:

| 元 | v71(潰していた) | v72(黙る) |
|---|---|---|
| `だったら、返さないと。──頭より先に、口が動いていた。` | `…返さないと。、頭より先に…` | `…返さないと。` + 〈520ms〉 + `頭より先に…` |
| `「────ああ」` | `、ああ` | 〈520ms〉 + `ああ` |
| `「……深度470。…」` | `、深度470。…` | 〈360ms〉 + `深度470。…` |

**行頭・行末の沈黙も残す。** 「言いよどんでから話す」「言いかけて途切れる」は
この脚本では意味を持つ。

### ⚠️ 一言も喋らない行がある

`「…………」` のような、間そのものが台詞の行。記号を外すと**空になる**。
空のまま返すと `speakLine` が即 onEnd を呼び、**AUTOがその行を一瞬で送ってしまう**
(間が消えるだけでなく、通常の行より速くなる)。

点の数 × 240ms(400〜1600msに収める)の沈黙を返すようにしてある。
`「…………」`→960ms、`「……」`→480ms。

**全16話に通して parts が空になる行が0件であることを検証済み。** ここを変えたら再確認すること。

### 行の長さで速さを変える

全部同じ速さだと平らになるので、短い行は溜めて長い行は流す。

| 本文の長さ | 速さ |
|---|---|
| 14字以下 | ×0.93(溜める) |
| 15〜59字 | ×1.00 |
| 60字以上 | ×1.04(流す) |

心の声(`「(…)」`)はさらに ×0.96、音量0.8。

### ⚠️ 声と曲は下げないと相殺する

v71/v72 では読み上げとBGMを素のまま同時に鳴らしていた。実機で確認した結果、
**同じ音量帯でぶつかって声も曲もぼやける**(翔平の表現では「相殺しちゃう」)。

v73 で読み上げ中はBGMと環境音を **0.3(約-10dB)** まで下げる。

#### ⚠️ ゲインを既存ノードに書くと必ず喧嘩する

`bgmGain.gain` は**5箇所から書き換えられている**(`playBgm` / `stopBgm` /
`btnBgm` のトグル / `ensureCtx` / MUSIC ROOM)。`ambGain.gain` も `updateAmb` が触る。
ここへ割り込むと、どちらかが相手の値を上書きして破綻する。

だから**独立した段を1つ挟んだ**。既存のゲインは一切触らない。

```
bgmGain ─┐
         ├→ duckGain → destination
ambGain ─┘
```

`duckGain` だけを `voiceDuck(on)` が触る。下げは時定数0.06秒(速く)、
戻しは0.18秒(ゆっくり)。戻しが速いと曲が波打って聞こえる。

#### ⚠️ 戻し忘れると曲が小さいまま戻らない

これが一番怖い壊れ方。終了経路は3つあり、**全部で戻す必要がある**。

| 経路 | 戻す場所 | 実測 |
|---|---|---|
| 普通に読み終わる | `vsDone()` | 0.3 → 1.0 |
| 発話中に声をOFF / 別の行へ | `stopVoice()` | 0.301 → 0.999 |
| `onend` が来ない端末 | 見張り → `vsDone()` | 0.301 → 1 |

`btnBgm` の ON/OFF 操作中も `duckGain` は 1 のままで干渉しないことを実測済み
(♪OFF → `bgmGain`=0 / `duck`=1、♪ON → `bgmGain`=0.9 / `duck`=1)。

**間の最中もダックは戻さない。** 1行のあいだ下げ続ける。
沈黙ごとに戻すと曲が波打つため。

### TTSの仮の配役

`VOICE_CAST` に話者ごとの `rate`(速さ)と `pitch`(高さ)がある。
エルザは低くゆっくり(0.92/0.86)、ユウジは高く速く(1.10/1.10)、
《トランジスタ》は最も低い(0.88/0.70)。**収録が入ればこの表は使われなくなる。**

ユウジの心の声(`「(…)」`)は音量0.8・速さ0.96倍で少し引いて読む。

## 19. 進行データとUI(v74〜)

### ⚠️ セーブは「枠」ではなく「話ごと」

不満の中身は**「やり直すと上書きされる」**だった。枠を3つ並べるより
**話ごとに位置を持つ**方が効く。第一話を遊び直しても最終話の位置が死なない。
チャプターの読了印も同じデータで済むので、増えるのは1キーだけ。

```js
localStorage["crc_prog"] = {
  v:1,
  eps:{ "7":{i:99, done:false, at:...}, "1":{i:0, done:true, at:...} },
  last:"7"            // 「つづきから」が指す話
}
```

| キー | 役割 |
|---|---|
| `crc_prog` | **これが本体。**話ごとの位置と読了 |
| `crc_save` | 旧形式。**読みは引き継ぎ用のみ。書き込みは継続**(前の版に戻しても位置を失わないため) |
| `crc_flags` | 選択肢のフラグ。従来どおり全周回で共有 |

**`crc_prog` が無ければ `crc_save` から自動で引き継ぐ。** 既存プレイヤーの位置を失わせないため。
実測で `{ep:"7",i:99}` → `eps["7"].i=99 / last="7"` になることを確認済み。

### 遊び直しの挙動

| チャプターの状態 | 印 | タップしたら |
|---|---|---|
| 未着手 | 無し | 頭から |
| 途中 | `▶ 49%` | **続きから**(`↺` で頭から) |
| 読了 | `✓ 読了` | 頭から |

**どちらになるかはボタンの印で見えている**ので驚かない、という考え方。
「つづきから」ボタンは**どの話が再開するかを文字で出す**(`つづきから ―― 第三話`)。
`last` が入れ替わっても不意打ちにならないため。セーブが無いときは**ボタンごと隠す**。

読了済みの話を遊び直している途中で抜けると、次は頭からになる(`done` が優先)。
印が `✓ 読了` のままなので挙動とは一致している。

### ⚠️ LOGから戻るとき、0〜iを再生し直してはいけない

通らなかった分岐の背景や曲まで拾ってしまう。
**表示した時点の世界を `pushLog` で控えておき、それをそのまま戻す。**

```js
backLog.push({n, t, i:state.i, ep:state.ep, w:worldNow()});
```

`worldNow()` が持つのは `bg / dim / spr / bgm / bgv / amb / wash / bat` の8つ。
これらは `run()` の**分岐側**で記録する ── `setBg` の中ではなく。
`bg` が `bgv` を止めるといった**命令の副作用まで1箇所で見たい**から。

**戻れるのは同じ話の中だけ。** 別の話へ飛ぶとフラグと世界が噛み合わない。
`e.ep===state.ep` で門を閉じてある。

**フラグは巻き戻さない。** 既に起きたことは起きたままにする。

戻った先から先の `backLog` は捨てる(同じ行が二重に積まれないように)。

### ⚠️ backLog は話が変わると消える(v74での変更)

以前は話をまたいで220行貯まり続けていた。v74 で `startGame` が毎回クリアする。
**別の話の行が混ざると、戻れない行が「戻れそうに見える」**ため。
前の話のログを読み返す用途は失われた。必要なら `ep` ごとに分けて持つこと。

## 20. 音質の方針 ── 本体は試聴、本物はSunoに(v75〜)

### 決めたこと

本体に高音質を積むのはやめた。**本体の音は試聴音源**と位置づけ、
**本来の音は作者のSunoへ聴きに行ってもらう。**

容量の都合を言い訳にするのではなく、設計として成立する:
音楽配信は実際そうなっているし、翔平が作曲者本人なので、
**聴きに来てもらうこと自体が目的になる。**

### 実装

MUSIC ROOM の解説文の下に、**今表示している曲の Suno ページへの直リンク**を置いた。

```js
const SUNO_ID = { bara:"7e15f374-…", crimson:"5d8d0013-…", … };
function sunoLink(key){
  return SUNO_ID[key] ? "https://suno.com/song/"+SUNO_ID[key] : SUNO_USER;
}
```

**IDは各mp3のコメントに埋まっていたものを拾った。** Sunoが書き出し時に
`made with suno; created=…; id=…` を埋めている。

**URLの形は実機で確認済み**(翔平が `https://suno.com/song/<id>` を踏んで到達)。
このコンテナからは suno.com に出られないので、**ここを変えたら翔平に踏んでもらうこと。**

| | |
|---|---|
| 曲ページへ飛ぶ | 10曲 |
| アーティストページに落とす | `requiem` のみ(IDが無い。別経路で書き出したらしい) |

LINER NOTES 末尾のアーティストリンクは**残してある**(読み切った人へのご褒美として機能している)。

### ⚠️ 新しい曲を足したら SUNO_ID にも足す

足し忘れるとその曲だけアーティストページに落ちる。壊れはしないが、
**曲ページに飛ばない曲が黙って混ざる**ので気づきにくい。
IDは mp3 のコメントから拾える:

```bash
ffmpeg -i 曲.mp3 2>&1 | grep -o 'id=[0-9a-f-]\{36\}'
```

### 測ってわかっている音質の現状(v75時点)

| | |
|---|---|
| 全11曲 | **56kbps モノラル 48kHz**(gag と obscure は 48kbps) |
| 周波数の上限 | 多くは **15.1kHz**。**bara 11.9k / gag 11.4k / obscure 11.1k** |
| 全曲の合計尺 | 38分00秒 / 実体 15.0MB / base64 19.9MB |

**高ビットレートで焼き直しても上限は1Hzも動かない**(192k/320kで実測)。
捨てられた高域は戻らないので、**上げるにはSunoの原曲から焼き直すしかない。**

**bara だけが異常。** 56kbpsの他の曲は全部15.1kHzまで出ているのに
bara は11.9kHzで止まっている。元が既に劣化していた可能性が高い。

通しプレイ1回で聴いている時間を測ると **bara 26分(36%) / gag 21分(29%)** で、
**この2曲だけで改善できる分の100%をカバーする**(残り9曲は既に15.1kHz)。
原曲から56kbpsで焼き直すだけなら**容量もメモリも増えない。**

## 23. 友人のテストプレイで出たこと(v77で対応)

### ⚠️ 「下にスクロールしないとチャプターにいかない」は、実は画面外ではなかった

全機種で測ったところ、**最小のiPhone SE(表示領域375x553)でも1話目は画面内**にあった
(上端343px)。扉絵は `aspect-ratio:16/13` で画面幅から高さが決まるので、
どの端末でも画面の半分より小さい。

**本当の原因は「表紙に見えること」。** 扉絵の中に
`― CYBER ROSE CRIMSON ―` と `SELECT CHAPTER` が乗っていたため、
「物語をはじめる」を押したのに**また表紙が出た**と受け取られ、
下にリストがあっても手が止まる。

**指摘の言葉(スクロール)と原因(見た目)がずれている例。**
報告をそのまま実装せず、measure してから直すこと。

### 対応: 扉絵の中に行き先を置いた

```
― CYBER ROSE CRIMSON ―
   [ ▶ 第一話から読む ]      ← 進行があれば「▶ つづきから ―― 第四話」
      ▼ 話を選ぶ            ← 押すと一覧まで送る(飾りではない)
```

初見が**16個から選ばなくて済む**のが要点。一覧は「他も選べる」用に残す。
`paintHeroStart()` が `paintChapters()` から毎回呼ばれ、進行に応じて文言と
飛び先が変わる。

### ライナーノーツは独立画面にした

曲の解説ではなく**作者自身の言葉**なので、MUSIC ROOM の曲リストの下に

## 22. Netlifyで公開する場合(未実施・準備だけ済み)

`netlify.toml` を置いてある。リポジトリを繋げばそのまま効く。

### ⚠️ 設定ファイルが無いと別のアプリが公開される

**`vite.config.js` と `package.json` があるので、Netlify も Vercel も
自動で `npm run build` を走らせて `dist/` を公開しようとする。**

```
"build": "vite build && cp dist/app.html index.html ..."
dist/app.html  215KB  ← 焼肉ロス管理アプリ
```

**`crc/` はビルド対象外なので、ゲームが1バイトも含まれない。**
`netlify.toml` で `build.command` を明示すると自動判別が止まる。

```toml
[build]
  command = "echo '…'"     # 空にせず何か書く。空だと自動判別が生き残ることがある
  publish = "."
```

### `crc/_headers` は効かなくなる

Netlify は `_headers` を**公開ディレクトリの直下**で探す。`publish = "."` なので
`/_headers` を見る。`crc/_headers` は読まれない。
キャッシュ制御は `netlify.toml` の `[[headers]]` に移してある(一元化)。

| `/crimson` | 同じもの(口頭で伝えやすい短い方) |
| `/` | 焼肉ロス管理アプリ(今まで通り) |

## 21. セキュリティの現状(v76時点)

テストプレイを人に配るにあたって一度通して見た結果。

### 攻撃面がそもそも無い

**サーバーが無い。アカウントも、決済も、文字入力欄も1つも無い。**
HTML1枚が手元で動くだけなので、乗っ取る対象が存在しない。

実測で確認したこと:

| 調べたもの | 結果 |
|---|---|
| 外部への通信(`fetch` / `XMLHttpRequest` / `sendBeacon` / `WebSocket`) | **0件** |
| 位置情報・カメラ・マイク・Cookie | **0件** |
| 文字列からコードを実行する類(`eval` / `new Function` / `document.write`) | **0件** |
| 外部ホストへの参照 | **suno.com のみ**(作者自身のページ、`rel="noopener"` 付き) |
| リポジトリ内の秘密情報(APIキー・トークン・メールアドレス) | **無し** |

**解析も計測も一切入っていない。** テスターが何をどう遊んだかは、どこにも送られない。

### 文字をHTMLに流し込む箇所

`innerHTML` への代入は7箇所。うち5つは空文字か固定文字列。
動的なのは **EDクレジット / LOG / 曲名** の3つで、**全部が作者の書いた定数**。
外から文字が入る口が無いので、注入の経路が無い。

v76 でLOGのエスケープを**本文と話者名の両方**に揃えた(`& < > "`)。
穴があったわけではないが、**片方だけ守っていると後から口が増えたときに気づけない**ため。
細工した行をLOGに混ぜて、タグとして解釈されず文字のまま出ることを実測済み。

### ⚠️ 配信元が共有ドメインであること

`rawcdn.githack.com` は **githack で配信されている全ページと同じオリジン**。
つまりセーブデータ(`crc_prog` / `crc_save` / `crc_flags`)は、
**他のgithack配信ページからも読み書きできる場所に置かれている。**

| | |
|---|---|
| 入っているもの | 進行位置・読了・選択肢のフラグだけ |
| 入っていないもの | 個人情報・認証情報の類は一切無し |
| 現実的な被害 | **セーブを書き換えられる**程度 |

気にするなら、専用ドメイン(Netlify / GitHub Pages)に移せば解消する。
**今の用途(身内のテストプレイ)では見合わない。**

### リポジトリは public

`reference/settings.md`(正史・プロット・伏線表)も `.claude/skills/` も
**誰でも読める。** raw.githack が公開リポジトリとして配信できているのはそのため。
ネタバレを含むので、**公開範囲を変えたいなら private にする判断が要る**
(ただし private にすると raw.githack での配信が止まる)。
